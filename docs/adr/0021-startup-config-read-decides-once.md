# ADR-0021 — A startup Config read refuses anything but a missing file

Status: accepted
Date: 2026-11-14
Related: ADR-0014 (settings file), ADR-0020 (`config.json` and the config table)

## Context

`config_store.loadOrDefault` and `loadOrDefaultInDir` returned `Config.default()` for **every** failure: a file that could not be read, one that did not parse, and one holding a value the config table rejects all looked like a first start with no file. The module's `Error` set advertised five members (`OutOfMemory`, `InvalidJson`, `UnsupportedValue`, `WriteFailed`, `System`), while the read path could produce one of them — `OutOfMemory` from `configPath`. So every caller's error branch was written, compiled, and never exercised: `setCurrentFile`'s `try`, the Android host's `catch`, and the desktop entry's `catch unreachable` were all dead for a bad file.

Nothing in the repo stated what the read *ought* to do, so the tests could not either: `config_store.zig` asserts "a bad value, a non-object config or unparsable bytes load the defaults", which is a snapshot of the implementation's choice rather than a check on it. Any change to the choice would have been written into the same commit as its test, and the two would agree again.

The write path already refused: `writeFailed` logs the reason and returns `Error.WriteFailed` (it returned `Error.System` until the two failures were told apart, below).

## Decision

The rule is decided once, in core, and every front end only renders its outcome.

1. **File missing** (`error.FileNotFound`) → `Config.default()`, one info line (`expected: … yet`), startup proceeds. A first start is normal.
2. **File present but unreadable, unparseable, or holding a value the table rejects** → one log line carrying `@errorName`, then `Error.System`. Startup does not proceed.
3. **A write failure does not stop the boot.** `writeFailed` logs its one line and returns `Error.WriteFailed`; `resolveStartupConfig` has already produced a usable config from the successful read, so it proceeds and the failure stays a logged persistence miss. A refusal sentence would send the player to clear data or repair a file that is sound. The write's own sentence belongs to the action that asked for the write, not to startup.
4. **The reason is logged, the return collapses.** Every failing read branch logs the system name it caught and returns `Error.System`, the way `writeFailed` and `game_engine`'s open arms already do. A caller that needs the distinction reads the log line; no arm re-words it.
5. **The rule covers every read of `config.json`**, which makes `setCurrentFile`'s read strict too: it reads the Config it must preserve, so a file it cannot read is refused rather than quietly repaired. The read inside `save` / `saveInDir` stays lenient — it holds the Config already and may repair the file it is about to rewrite, and its one line says it is repairing rather than that the read refused. That repair is tested with a file that does not parse: a file whose read fails for root cannot be written either, so the unreadable variant has no fixture that runs as both.
6. **A test asserts the rule, not the implementation.** Each case in the decision above gets a test that would fail if the code took the other reading; a test that both readings satisfy is not evidence and must not be cited as such. The fixture must fail for the user the suite runs as: an unreadable file is a directory standing where `config.json` would be, not a file whose read permission was taken away, which root reads anyway. Where both readings can reach the same outcome — a directory cannot be written over either way — the test asserts the *line the reading logs* instead: one refusal from the read, or that plus a second from the write.

## Consequences

- One behaviour for a bad file on every arm: it is refused, with its reason in the log, instead of being replaced by defaults.
- A first start never stops: only a file that exists and cannot be used refuses.
- The failure channel of `Error` is now used, so the callers that already handled it are reached: the `-r web` host's pointer write refuses instead of repairing a corrupt file, and the Android boot reads settings through the same seam, so a refused file starts no loopback server at all — the boot records the failure for Java to show, instead of defaulting and serving a file nobody could read.
- The desktop entry's `catch unreachable` on this seam was already reachable through `save` before this decision and must become a `try`; that defect is its own change, not this rule's. It is now a `try`: the seam declares `error{System}`, which `main` already carries, so a refused startup exits 1 with core's line on stderr instead of trapping.
- `config.json` keeps its shape and `current_file` its meaning, so an older app still reads it.
- Front ends gain no text for the refusal: core owns the log lines and the sentences. The Android boot shows core's `ANDROID_SETTINGS_REFUSED_MSG` (clearing the app's data in the Android Settings app is the way out) on its boot-failure page and in the toast, read through one accessor that is empty when startup did not fail; its own WebView advice stays for the failures core did not word. The loopback host answers a `POST` or `DELETE /current-file` whose pointer write the store refused with a 500 whose body is core's sentence (repairing or deleting the file is the way out), so the page can show the player what to fix instead of a request that silently did nothing. Which sentence follows what the store refused: `SETTINGS_REFUSED_MSG` for a settings read it would not use, and `SETTINGS_WRITE_FAILED_MSG` for a settings write that failed — a full disk or a folder this user may not write leaves a file that is sound, so that sentence names the space and the permission instead of sending the player to repair what is not broken. A refused forget touched nothing, so it answers that cause's sentence as it stands; a refused save follows bytes that already landed, so it answers `WRITTEN_SETTINGS_REFUSED_MSG` / `WRITTEN_SETTINGS_WRITE_FAILED_MSG` (`src/core/flow/save.zig`), which state that the game file was written, keep the same cause's repair, and never call the save the current file — the session kept the file it had. The terminal shows the same sentence, from the `written_not_current` answer `Storage.saveGame` reports, instead of a status that reads as if nothing happened. The store tells the two apart by the error it returns (`System` for a file it will not use, `WriteFailed` for a write the system refused), each with its one log line. A store error that is neither cause is nobody's refusal: the player gets core's generic failure — `SAVE_FAILED_MSG` for a save, `FORGET_FAILED_MSG` for a forget — rather than a repair that does not apply. The host names the system message in the `X-Sudoku-Failure` header while the body stays core's sentence, and the page hands that message on as the answer's reason, so the one line core's flow (or the save's `writeFailed`) logs carries the cause instead of only a status code: no adapter writes a second line for the same event. The host also names the refusal kind in the `X-Sudoku-Refusal` header, so the page hands core that reason instead of reading core's words back.
- **The forget's order is core's, and the refusal is a failed answer on the step.** A forget clears the current-file pointer first and deletes the file only once the clear landed, because the clear is the write the settings store can refuse: doing it first is what leaves the player's save on disk and the pointer naming it, while delete-then-restore would need the bytes cached and still lose an overwrite. The delete arrives as a callback in core's vtable idiom (`src/core/flow/forget.zig`), so neither the loopback host nor the native shell decides which write comes first. A delete that fails after the clear is logged once, naming the file and the reason, and is answered as success: the requested state was reached. The refusal is `.forgot = .refused` with the kind core keeps (`settings_unreadable` / `settings_unwritable`); the startup flow ends on that kind's sentence, the terminal draws it as a status line, and the page's step runner answers the step instead of deciding the flow's fate. Only the two store errors this app knows how to repair are refusals (`System`, `WriteFailed`). A forget that fails for any other reason — a store error with no repair, a bare 500, a dropped connection from the host — arrives as `.forgot = .failed` carrying the reason: the startup flow is the one site that sees every failure, it logs that reason once, and it ends on `FORGET_FAILED_MSG`, because telling the player to repair a file that may be sound, or to relaunch for a dropped connection, would be a sentence that is not true. A save keeps the opposite order (bytes first, pointer second), because a pointer naming bytes that never landed would make the next restore load the wrong game. A healthy settings file leaves every page and terminal path as it was.
- **A refused pointer write is a step answer, and a load that cannot be remembered says so.** The page hands core the refusal kind the host named (`X-Sudoku-Refusal`) instead of reading the host's sentence back, so `written_not_current` reaches core and core's `WRITTEN_SETTINGS_*` sentence is the only status the player sees: no page text, and no failure sentence after it. A refusal the host named no kind for keeps the old answer (the host's body plus core's failure prompt). The same kind arrives on a load the terminal tried to remember: `Storage.persistCurrentFile` reports it, the game is drawn, and core's `LOADED_SETTINGS_*` sentence (`src/core/flow/command.zig`) says the game was loaded while the next launch will not reopen it, with that cause's repair — the terminal words nothing itself, and a store error that is no refusal is logged there and words nothing. The host maps a store error to its refusal once, through core's `refusalFor`, so both `/current-file` arms answer from one map; an error that map does not cover answers core's generic failure with the system message in the `X-Sudoku-Failure` header and no refusal header, and the host writes no line of its own because core's flow records the reason once. No JavaScript module keeps a list of kinds either: the wasm boundary validates the reason and rejects an unknown one with core's failure prompt, so a kind is named once, in core.
- A refused startup exits 1 by returning the seam's error, so a Debug build also prints the runtime's `error: System` and a return trace after core's line; a release build prints the line alone. That is accepted: the trace is diagnostics for us, never seen by a player, and silencing it would mean `main` swallowing an error, which is the defect this ADR exists to undo.
